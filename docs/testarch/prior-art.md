## 1. THE EXISTING UNIT LAYER

### 1.1 Project shape and why it exists

`tests/Dodona.Tests/Dodona.Tests.csproj` — xunit 2.9.2, Microsoft.NET.Test.Sdk 17.12.0,
`net8.0`, `<Nullable>enable</Nullable>`. One `ProjectReference` only: `..\..\src\Dodona\Dodona.csproj`.
**No reference to DodonaUi, DodonaShim or DodonaFakeAgent.**

Two load-bearing comments in the csproj:

- *"The eleven .ps1 suites verify BEHAVIOUR through the real binaries — that is their whole value…
  What they were also doing, incidentally, was covering algebra with no I/O in it: Claims is 53
  lines of string comparison, and the only way to exercise it was to create a ticket, which needs a
  workspace, which needs a daemon. **This project takes that half. The suites keep the other half,
  undiminished.**"* — this is the project's own statement of the split the new plan is extending,
  and it explicitly promises the suites are not diminished. Constraint 1 and 3 already have a
  charter here.
- *"Version-pinned to what is already in the machine's package cache, on purpose: adding a
  verification step that needs the network is adding a way for verification to be unavailable
  exactly when it is wanted."* — **do not add a NuGet package** (no Moq, no FluentAssertions, no
  NSubstitute) without confronting this. It is a stated decision, not an accident.

Visibility: `src/Dodona/Dodona.csproj:26` carries
`<AssemblyAttribute Include="System.Runtime.CompilerServices.InternalsVisibleToAttribute">`, and the
csproj comment says why: *"The classes under test are `static class` with no accessibility modifier,
i.e. internal. Dodona.csproj grants this assembly access rather than the types being widened to
public for the sake of a test — the design's own choice about what is API stays the design's
choice."* **This is the established mechanism for reaching internals; use it, do not widen types.**

### 1.2 Naming and tally

- Test names are **sentences with underscores**, matching acceptance-check style:
  `Two_identical_paths_overlap`, `A_sibling_with_a_shared_prefix_does_not_overlap`,

### 1.4 THE ANTI-DRIFT MECHANISMS ALREADY IN THE UNIT LAYER — this is the seed of the plan

There are **four distinct mechanisms**, and only one of them is the "reflection" one the task
named. All four are cheaper and stronger than a hand-maintained fake.

**(a) STRUCTURAL / ENUMERATION ASSERTION.** `DictationTests.Dictation_never_submits`
(`tests/Dodona.Tests/DictationTests.cs:35-51`):

```csharp
foreach (var name in Enum.GetNames<DictationAct>())
{
    var n = name.ToLowerInvariant();
    Assert.False(n.Contains("submit") || n.Contains("send") || n.Contains("execute"),
        $"DictationAct has a member meaning send: {name}");
}
```

Its own doc comment: *"It is asserted structurally rather than behaviourally, which is stronger:
there is no value `Dictation.Decide` can return that MEANS send, so no caller can route one there
even by mistake."* `docs/VOICE-ENGINE-PLAN.md:88` calls this "by reflection" and adds: *"If your
work makes that check red, you have broken the operator's one hard constraint, not found an
inconvenience."*
The other enumeration case is `DictationTests.cs:202`,
`The_state_machine_can_always_recover_and_always_stop`, which walks `Enum.GetValues<ListenState>()`
and demands every state can reach `Off`. **These are the ONLY two enumeration-driven assertions in
the whole unit layer** (grep for `Enum.GetNames|Enum.GetValues` returns exactly those two lines).
There is no reflection over methods, properties or types anywhere in `tests/Dodona.Tests/`.

**(b) ROUND-TRIP THROUGH BOTH REAL SIDES — the most important prior art in the tree.**
`AskTests` (`PureLogicTests.cs:1454-1613`) calls the **real producer** (`Ask.RepoInitCandidates`,
`Ask.RouteCandidates`, `Ask.LandCandidates` — the daemon's writers) and feeds the result to the
**real consumer** (`Ask.Choices` — the window's parser). No fake exists, so nothing can drift. Its
doc comment states the rule the whole new plan wants:

> *"the daemon WRITES `questions.candidates` and the window PARSES it, and the whole of D-L4 is
> that there is one component over one row. A parser that disagreed with the writer would put the
> divergence in the one place no acceptance check looks — inside a string."*

This is **"count the wires, not the cases" already implemented**: the acceptance suite (`ui-ask`)
proves the row reaches the screen once; the unit layer proves every candidate shape round-trips.

**(c) INJECTED PROBES AT THE FUNCTION BOUNDARY.** `Trees.Locate(path, projects, dirExists,
fileExists)` takes its two filesystem probes as delegates. `TreesTests.cs:24-27` passes array
lookups; production passes `Directory.Exists` / `File.Exists`. One function, two callers, no
parallel implementation to drift. Comment: *"`Locate` takes its two probes as parameters so this
file can describe a repository, a worktree inside it and a bare folder without creating any of
them — which is what keeps `dev test unit` at about a second."*

**(d) STATIC-METHOD EXTRACTION SO A UNIT TEST SEES WHAT NO SUITE CAN.**
`Daemon.ClaudeArgs` (`src/Dodona/Daemon.cs:2846`) was made `internal static` explicitly for this.
Its own doc comment:

> *"Static is not tidiness either: with no `this` it is callable from `unit`, so 'the permission
> mode in the argv is the one this config asked for' costs a millisecond to hold instead of eight
> seconds of daemon — **and the fake agent takes no claude flags at all (`IsClaude` is false for
> it), so no acceptance suite can see this argv.**"*

`PureLogicTests.cs:973` states the same from the test side:

> *"`Daemon.ClaudeArgs` is T2's last link. The event a suite reads reports the CONFIG it resolved;
> this is what pins that the config's permission mode actually reaches the process's argv — and it
> can only be checked here, because `IsClaude` is false for the suites' fake agent, so no suite ever
> builds a claude argv at all."*

And `Projects.PromptDirMismatch` (`PureLogicTests.cs:966-971`): *"**It compiles clean**, it has
already happened once (M5.1), and no acceptance suite can see it, because the prompt lives in an
argv nothing reads back."*

**THE DIRECT IMPLICATION FOR THE PLAN.** The fake agent already creates a *permanent blind spot*
in the acceptance layer — everything downstream of `IsClaude()` is invisible to all 15 suites.
That blind spot is covered today only by unit tests. Any new fake will create its own blind spot;
the plan must name each one and put a unit test opposite it, the way `ClaudeArgs` did.

### 1.5 HOW UNIT CHECKS ARE PROVED — `dev prove` REFUSES the unit suite

`tools/dev.ps1:1178-1196`. If any named suite is `unit`, `Do-Prove` **aborts** with a three-step
substitute. The three recorded reasons it was broken before the refusal:

1. the HEAD build compiled `tests\Dodona.Tests`, so a unit test naming a symbol the change ADDS
   failed to compile → prove aborted `"HEAD does not build"` and **took every acceptance check in
   the same run down with it**;
2. `Start-Suite` would then abort `"no suite 'unit'"` (there is no `tests\unit-acceptance.ps1`);
3. `Run-Unit` builds and tests `$repo` — **the working tree** — so the verdict would be the change
   measured against itself. *"A silently wrong proof is worse than no proof; it is the
   believed-a-green-check disease with a certificate."*

The stated honest limit: *"a NEW pure function cannot be failed by a HEAD that does not contain
it."* Prescribed substitute (also `docs/VOICE-INPUT-PLAN.md` D-V11):
**break the function on purpose → `dev build` → `dev test unit` → read the red → revert → record
the red in the commit.** `DictationTests.cs` and `SpeechStreamTests.cs` do exactly this: every
check carries a `PROVED RED by …:` line with the literal assertion message. Examples:

- `Dictation_never_submits` — *"PROVED RED by adding `Submit` to DictationAct and returning it for
  'enter': `Assert.False() Failure -- DictationAct has a member meaning send: Submit`"*
- `Splice_lands_at_caret` — *"PROVED RED by returning `(heard, text.Length + heard.Length)`:
  `Expected: 11  Actual: 22`"*
- `Endpoint_promotes_the_last_interim` — *"making `Kind.Endpoint` return null instead of promoting
  gave `Assert.NotNull() Failure: Value is null`"*

**A related trap, recorded (`VOICE-INPUT-PLAN` D-V11 and `VOICE-ENGINE-PLAN` §11):** a driver ran
`dev test unit` **without building**, hit P1.5's stale-build refusal on all six checks, and
reported **VACUOUS** — *"a fake verdict about a run that never happened."* Treat **DID-NOT-RUN as
distinct from VACUOUS**. Also: *"A check whose subject does not exist on HEAD reads MISSING, not
PROVEN, if it sits behind a guard"* — `clicking_the_mic_toggles_listening` was inside `if ($micBtn)`
and never ran.

### 1.6 WHY `unit` IS IN `SoloSuites`

`tools/dev.ps1:782` — `function SoloSuites { , @('unit', 'voice') }`. The reason, stated at
`tools/dev.ps1:661-668` and in CLAUDE.md §3:

> *"THE RULE IS: only one thing may COMPILE at a time. A compile writes `src\<proj>\obj\` and
> `src\<proj>\bin\`, and every suite copies its binaries out of `src\...\bin` at startup
> (`Use-TestBinaries`). Exactly one entry in the set compiles: **unit** is `dotnet test`, which
> builds Dodona.Tests AND its ProjectReference to Dodona — straight into `src\Dodona\bin`. So it
> runs alone."*

**This is a build-output collision, not a flakiness or contention argument.** It is the ONE solo
reason that is structural rather than measured, and it has a direct consequence for the plan:
**growing the unit project does not make the solo problem worse in kind, but every second added to
`unit` is serialised in front of the wave.** Note `unit` first in `AllSuites`
(`tools/dev.ps1:51-58`) — *"it is the cheapest thing that can fail."*

Two ways out exist and neither is proposed anywhere today (so both are open, not rejected):
`dotnet test --no-build` against an already-built output, or `-p:BaseOutputPath=<temp>\` the way
`publish` does (`src/Dodona/Program.cs`, publish branch, *"Only bin is redirected: obj must stay
put"*) — which is exactly why `m4` is NOT solo despite running a real build
(`tools/dev.ps1:737-746`).

**`voice`'s solo reason is different and must not be conflated**: it is a *measured* window-suite
cascade (`tools/dev.ps1:783-795`) — 70.5 s / 3 failed in a wave vs 40.3 s / green alone.

## 2. THE EXISTING FAKES — and how each is (or is not) kept in sync

Answering the question that matters most: **by construction, by a test, or by hand and hope?**

### 2.1 `src/DodonaFakeAgent/` — the stand-in for `claude`

**545 lines, one file** (`src/DodonaFakeAgent/Program.cs`).

**Protocol it speaks.** `claude -p --input-format stream-json --output-format stream-json`, as
observed in `spikes/SPIKE-1-resume.md` / `SPIKE-2-shim.md`. Reads one JSON line per turn from
stdin, extracts `message.content[0].text`; emits `system/init` with a `session_id` once, then per
turn: `assistant` events (`tool_use` blocks with `file_path` or `command`; `user` events with
`is_error` tool_results; `system/thinking_tokens`) and one `result` event.

**How a suite drives it.** Not by an env var — by **`dodona.json`'s `"agent"` field**
(`src/Dodona/Daemon.cs:19`, `Config(string Main, string[] Verify, string Agent = "claude", …)`),
or per-command `--child <path>` (`Daemon.cs:1259,1285,1306`; e.g.
`tests/m1-acceptance.ps1:140` → `Dodona @("ticket-agent","1","--child","$bin\DodonaFakeAgent.exe")`).
Turn behaviour is **directives embedded in the user text**:
`sleep:N`, `say <text>`, `tool:Name:arg`, `bash:<cmd>`, `toolfail:<m>`, `think:N`, `env:NAME`,
`cwd`, `brief`. Roles come from `DODONA_LANE_ROLE`: `compressor`, `brain` / `brain-hi`, `router`,
`concierge-lo` / `concierge-hi`, each with its own directive vocabulary (`brainname:`, `brainlow`,
`hikind:`, `routeproject:N`, `routekind:`, `cxpick:N`, `cxws:`, `cxfolder:`, `cxdisagree:`).

**HOW IT IS KEPT IN SYNC WITH `claude`: BY HAND AND HOPE, WITH ONE NAMED EXCEPTION.**

- There is **no shared constant, no shared schema, no contract test** between the fake and the
  real wire. The fake references nothing (`src/DodonaFakeAgent/DodonaFakeAgent.csproj` has no
  ProjectReference — 556 bytes, standalone). This is **deliberate**, stated in
  `docs/LANE-BRIEFING-PLAN.md` **D-B7**: *"There is no shared constant (the fake agent references
  nothing on purpose); the drift is caught by `the_briefing_reaches_a_ticket_agent`, which reads
  `(none)` and goes red the moment the two spellings disagree."* The same sentence appears verbatim
  as a code comment at `src/DodonaFakeAgent/Program.cs:94-101` about `const string BriefEnd =
  "[/DISPATCHER]"` vs `Dodona.Briefing.TurnEnd`.
- So: **one string constant is guarded by one acceptance check.** The rest of the wire shape
  (`type`, `subtype`, `session_id`, `content[].type == "tool_use"`, `tool_use_id`, `is_error`,
  `result`) is duplicated by hand between `src/DodonaFakeAgent/Program.cs` and the real consumer
  `src/Dodona/LaneRuntime.cs:99-230`, and **nothing checks that they agree**. If Anthropic changes
  the wire, every suite stays green and production breaks — this is precisely the routing-ladder
  failure mode (CLAUDE.md §3) in a different costume, and it is not written down anywhere.
- The one mitigation in the tree is **CLAUDE.md §3's rule**: *"Every suite must exercise at least
  one path the way the OPERATOR runs it — autostart on, nothing pre-built by the test."*
  `brain-acceptance` does this (stops the classifier, restarts with `DODONA_NO_AUTOSTART` cleared,
  demands a `classified` event). That still uses the fake agent; it exercises Dodona's own wiring,
  not the wire format.

**THE SEAM THAT MAKES THIS FIXABLE, ALREADY IN THE TREE:** `src/Dodona/LaneSink.cs` —
`interface ILaneSink` with **six methods** (`Event`, `PaneEvent`, `PaneEventId`, `LaneSession`,
`LanePresence`, `KvSet`). `LaneRuntime` writes only through it. Two real implementers today
(`Store`, `ConciergeStore`). Its doc comment explains it exists so *"the concierge can run
management model sessions over the SAME shim wire the workspace daemon uses — the stream-json
parsing, the presence derivation, the exactly-once seq dedup, the turn-final detection — without
owning a workspace Store"*, and: *"Six method signatures were the cheaper answer."*
`LaneRuntime.HandleShimLine` (`LaneRuntime.cs:93-230`) is the real wire parser and is currently
**unreachable from the unit project** (no `LaneRuntime.` reference in `tests/Dodona.Tests/`).
This is the single highest-value existing seam for the plan.

**THE FAKE'S OWN DESIGN RULE, worth copying:** every default is the *un-useful* answer.
`router` with no directive answers `unclear`; both concierge tiers with no directive answer
`none`/`low`. Comments at `Program.cs:51-53` and `:69-71`: *"an unclear verdict delivers NOTHING,
so a fake agent with no directive can never cause a silent wrong delivery inside a test"* and
*"a fake agent that guessed would hide the one path most worth testing."* **A fake that defaults to
success is a fake that manufactures false greens.**

**A trap the fake encodes twice, and the plan will hit it:** `routeproject:N` and `cxpick:N` are
**indices, not names**, *because a project NAME written into the sentence is matched IN CODE by an
earlier rung, so a rung-2 test written with a name passes at rung 1 having never reached the tier
at all — a check proving the opposite of what it claims* (`Program.cs:112-127`, `:59-62`).

### 2.2 `FakeRecognizer` — the dictation seam (`src/DodonaUi/Recognizer.cs`, 218 lines)

**Kept in sync BY CONSTRUCTION (shape) + BY A DECISION (semantics), and the semantic half is
documented.**

- **By construction:** `FakeRecognizer : IRecognizer` (`Recognizer.cs:74`). The interface
  (`Recognizer.cs:21-58`) declares `event Action<Dictation.Heard>? Heard`, `event Action<string>?
  Failed`, `event Action? Ready`, `void Start()`, `void Stop()`, `string Engine { get; }`. The C#
  compiler enforces that both implementations have the same shape. `DeepgramRecognizer` is the
  other implementer.
- **One landing site, stated as the mechanism:** *"Two implementations and ONE landing site:
  `MainWindow.OnHeard`. The real engine and the fake raise the same event into the same method,
  which is the `ui type` reasoning applied one layer down — a fake that fed a parallel path would
  prove nothing about the real one, exactly as `DodonaFakeAgent` stands in for `claude` without
  inventing a second lane runtime."*
- **The semantic drift risk is real and is written into the code.** `FakeRecognizer.Start()`
  raises `Ready` **synchronously** (`Recognizer.cs:98-107`); the real socket does not
  (`IRecognizer.Ready`'s comment, `Recognizer.cs:29-49`: *"'Start() returned' and 'we are hearing'
  are now two different facts"*, and D-E16: `Ready` fires on surviving a grace period). The
  comment says the synchronous raise is what *"keeps the 268 existing checks byte-for-byte
  unchanged"* — i.e. **the fake is deliberately easier than the real thing at the exact point the
  real thing is hardest**, and no check covers the difference. `DODONA_UI_MIC=hang` (D-E10) exists
  to reach the timeout branch, and `=fail` (D-V15) to reach the error branch.
- **Three independent locks stop a suite touching a device or a socket**, all in
  `tests/_workspace.ps1 Use-IsolatedDodonaHome` (lines 62-107), NOT per-suite:
  `$env:DODONA_UI_MIC = 'off'`; `Remove-Item env:DODONA_STT_TOKEN`;
  `$env:DODONA_STT_NO_CLI_AUTH = '1'` (because route 1 reads
  `%USERPROFILE%\.claude\.credentials.json`, which `DODONA_HOME` does **not** relocate). Comment:
  *"a rule every suite must remember is a rule one suite will forget."*
  `Recognizers.Create` checks `MicDisabled` **first, before constructing anything**
  (`Recognizer.cs:157-160`), and `voice:mic_off_opens_no_socket` pins the ordering *"because
  'connect then do not listen' would pass any check that only looked at the state."*
- **`Engine` is the drift indicator surfaced to the operator.** The fake reports `fake` in suites
  and `none` when it stands in for a failed real engine (D-E11) — *"'fake' would read, to anyone
  looking at `ui dump`, as though an engine were installed and working."*

### 2.3 `src/DodonaUi/Poses.cs` (341 lines) — deterministic UI fixtures

**Kept in sync PARTLY by construction, with a named hole.**

- **By construction:** a pose returns a real `Snapshot` record (`src/DodonaUi/Vm.cs:85`), the same
  type `Poller.cs:152` builds from the live store. `Snapshot`'s **positional** members
  (`PaneSnap?[] Slots, List<string> Tray, List<FeedSnap> Feed, PaneSnap? Overlay`) are
  compile-enforced: adding one breaks all 15 `new Snapshot(...)` call sites in `Poses.cs`.
- **THE HOLE:** everything added since is an `init` property with a default —
  `Ask`, `Quota`, `Bands`, `FocusedWorkspace`, `FocusedWorkspaceName` (`Vm.cs:91-102`). A pose that
  omits new state compiles clean and renders a state the product cannot produce. **This has already
  happened once**, and the fix is recorded at `Poses.cs:71-76`:
  > *"Every pose except boot-zero is a window looking at a workspace, so they all name one. Without
  > this they posed a state that cannot occur — panes present, no workspace — **which is how a
  > blank grid once rendered behind a passing test.**"*
  The remedy applied was a wrapper (`InWorkspace`), not a mechanism. **This is the clearest
  existing example of fixture drift producing a false green in this repo, and the plan should cite
  it.**
- **The rule that keeps poses honest is a prose rule, repeated four times** in `Poses.cs:20,26,30`
  and CLAUDE.md §3: *"Every new affordance owes a deterministic pose."* Nothing enforces it.
  `Poses.Names` (`Poses.cs:11-32`) is a hand-maintained `string[]` of 16 names; `Get`/`GetRaw` is a

  merely passes SLOWLY would then read as PROVEN — a fake RED, which is worse than a fake green."**;
  (5) every suite prints its tally; (6) name the incident in a comment.
- **`file-patching`** — heredoc `\\` collapse; **emit bare LF, never derive the newline from the
  working tree** (`core.autocrlf=true`; a 105-line insert became a 1214-line phantom rewrite;
  `sed -i` rewrites the whole file's endings); **match the BOM, do not let the writer choose it**
  (`.ps1` here carry UTF-8 BOM + CRLF; `.cs`/`.md` are CRLF, no BOM — `src/Dodona/Program.cs` has a
  BOM, `Daemon.cs` does not); parse-check every `.ps1` (**a `.ps1` that fails to PARSE never reaches
  `finally`**; backticks are the likeliest cause); read your own diff (`git diff --stat` vs
  `git diff -w --stat`), and **assert a replacement matched exactly 1**.
- **`probe-hygiene`** — isolate `DODONA_HOME`; binaries from `Use-TestBinaries`; **`dodona status` is
  not read-only** (it summoned four `claude -p --model haiku` processes and the session then spent
  two hours misdiagnosing its own leak as machine contention); no machine-wide mutation while a
  verification is in flight; never kill by name; clean up in `finally` and then check.

### 5.3 Issue #11 — the empty-detail failure

`tests/m1-acceptance.ps1:1121–1128`, check `a_promoted_lane_is_re_briefed_as_a_ticket_lane`.
Observed at `3b235ab` inside a wave on a **clean** machine; alone: 135 checks, **0 failed**, 38.6 s.

```
a_promoted_lane_is_re_briefed_as_a_ticket_lane: FAIL []
```

**The bug is a diagnosis bug, not a wait bug.** The check HAS the `Wait-Until` (25 000 ms) — it
throws away the wait's boolean, and the FAIL detail is the same variable the wait was filling in, so
a timeout prints `[]`. Fix is one line, the shape `ec28986` used on five siblings:

```powershell
$got = Wait-Until { ... } 25000 "the promoted lane reporting the briefing it was delivered"
Check 'a_promoted_lane_is_re_briefed_as_a_ticket_lane' ... "row-arrived=$got detail=[$promotedFlat]"
```

**Explicit instruction: "Do NOT lengthen the 25 s deadline."** *"A deadline is a ceiling only reached
when something is wrong; the underlying slowness is #3's subject."*

**The family and the general rule** (from #10, closed): five already fixed —
`workspace:the_answered_rung_records_that_the_operator_decided` (asserted on one query and printed a
second), `workspace:P3Cwd` (absent lane id → invalid SQL → threw out of the try block: **no tally

asserted), `m2:an_extended_claim_leaves_nothing_undeclared` (no wait at all in front of a row the
daemon writes after the command returns).

> **THE GENERAL RULE, verbatim from #10:** *"wait for the condition you are about to assert on,
> capture it once, then assert and report the same value."*

Also from #10, and directly binding on Constraint 1: *"**Why this is not `dev prove`-able**, and that
is not a reason to skip it: the assertion does not change, only when it is sampled. … The
verification is that the check still passes normally and that its FAIL detail now carries the row it
read — check the latter by pointing the query at a `kind` that does not exist."*
